# HPA-514 Generated Story References and Map-Scoped Dialogue — Minimal V1 Design

> Issue: HPA-514
>
> Baseline: `main` at `3c0c73fc9c21e2472436461a1b58c04e1aefa7fa`.
>
> Delivery: one implementation PR after this design lock. This document does not implement runtime behavior.

## Summary

Gliese already has a working story-secrecy boundary:

```text
Markdown story source
  → Rust parser/checker/compiler
  → deterministic generated Rust runtime catalog
  → narrow Tauri dialogue lookup
  → only requested prose reaches TypeScript
```

HPA-514 preserves that boundary and fixes two demonstrated maintenance gaps:

1. `src-tauri/src/story/reference.rs` manually copies IDs already owned by TypeScript content registries.
2. `get_npc_dialogue` accepts `mapId` but currently ignores it.

The implementation also adds two small supporting invariants:

- validate that each beat's `(map, primaryNpc)` pair exists in current map content;
- retain one source `beat_id` and `map_id` on each current NPC dialogue group.

No story-to-world packet, integration requirement DSL, fingerprint, consumer fixture, or HPA-495 adapter is added in V1. The repository has no real consumer for those surfaces.

## Verified repository facts

- The story package contains six prologue beats.
- Each current story NPC effectively maps to one beat and one map.
- `reference.rs` is a small set of five manually maintained ID arrays.
- The Rust checker and compiler consume those arrays for reference validation.
- `WorldScene` requests dialogue using the player's current `this.mapId` and a nearby map-local NPC.
- Wrong-map lookup is therefore not expected during normal shipped gameplay; map validation is a command-boundary invariant.
- Existing branch conditions, quest-summary booleans, intents, session IDs, browser fixtures, and save behavior already work.
- The checked-in HPA-495 repository specification is an art map package adapter for masters, exports, provenance, and validation.
- No `Area Expansion Packet` or `storyIntegration` implementation exists in the repository.

These facts define the V1 limit.

## Goals

- Replace hand-maintained Rust story-reference arrays with deterministic generated Rust sourced from authoritative TypeScript registries.
- Reuse the repository's existing committed `@generated` Rust and freshness-check pattern.
- Keep current beat Markdown and runtime interfaces compatible.
- Validate that a beat's primary NPC is actually placed on its declared map.
- Preserve beat and map identity once per NPC dialogue group.
- Enforce exact map context at the Tauri dialogue boundary.
- Add focused tests for generation freshness, placement validation, metadata compilation, and wrong-map rejection.

## Non-goals

HPA-514 V1 does not add:

- `story/generated/game-content-catalog.json`;
- Serde types or runtime deserialization for a content catalog;
- `story/generated/story-integration.json`;
- a new story-integration report format;
- selected-beat fingerprints or validators;
- HPA-495 fixtures or Area Expansion Packet fields;
- `integration-requirement` Markdown directives;
- route, encounter, visual, audio, spoiler, interior, reward, or discovery requirement schemas;
- character identity, placement, or presentation models;
- participant, region, or anchor fields on beats;
- generic quest-objective conditions;
- a beat-first runtime catalog;
- new request or response fields;
- a new session ID format;
- prose inference, geometry, asset generation, a world graph, or a scripting engine.

Any future story-to-world consumer must first define a concrete checked-in input need. Its contract belongs in a separately scoped ticket based on that real consumer.

## Minimal architecture

```text
Authoritative TypeScript content registries
  → Bun exporter
  → @generated src-tauri/src/story/reference.rs
  → existing Rust checker/compiler

Markdown beats
  → existing NPC-first Rust catalog
  → NpcStoryDialogue gains beat_id + map_id
  → exact-map invariant at Tauri lookup
```

There is no new cross-language JSON artifact.

## 1. Generate `reference.rs` directly

Add:

```text
tools/export-story-content-references.ts
```

The tool imports and executes the existing TypeScript content registries through Bun and renders the existing Rust reference module directly.

Generated shape:

```rust
// @generated by tools/export-story-content-references.ts. Do not edit by hand.

pub const MAP_IDS: &[&str] = &[...];
pub const NPC_IDS: &[&str] = &[...];
pub const QUEST_IDS: &[&str] = &[...];
pub const SHOP_IDS: &[&str] = &[...];
pub const ENEMY_IDS: &[&str] = &[...];

pub const NPC_PLACEMENTS: &[(&str, &str)] = &[
    ("guild-hall", "guild-master"),
    ...
];
```

`NPC_PLACEMENTS` uses `(map.id, npc.dialogueId)`, because story `primaryNpc` and runtime lookup use dialogue IDs rather than map-placement object IDs.

The exporter must:

- derive map IDs from `maps`;
- derive NPC IDs from the authoritative dialogue registry;
- derive quest, shop, and enemy IDs from their existing registries;
- derive NPC placements from each map's `npcs` collection;
- sort every output deterministically;
- reject duplicate IDs and duplicate `(mapId, dialogueId)` placements;
- escape Rust string literals correctly;
- render the complete file in memory before writing;
- write through a temporary file plus atomic rename;
- support `--check`, comparing exact bytes without writing.

It must not export coordinates, geometry, transitions, encounters, presentation data, prose, or art metadata.

## 2. Reuse current story command flow

Update the existing package scripts directly:

```json
{
  "story:check": "bun tools/export-story-content-references.ts && cargo run --manifest-path src-tauri/Cargo.toml --bin story_check -- --mode=draft --write-report --write-generated",
  "story:check:strict": "bun tools/export-story-content-references.ts --check && cargo run --manifest-path src-tauri/Cargo.toml --bin story_check -- --mode=strict --check-generated"
}
```

Do not add a second set of catalog commands unless another caller later needs them.

### Failure behavior

Draft mode intentionally refreshes generated references before Rust validation:

1. the Bun exporter derives and validates references independently from TypeScript content;
2. it atomically replaces `reference.rs` only after complete generation succeeds;
3. Rust story validation then runs;
4. if Rust validation fails, `reference.rs` remains a valid current derivative of TypeScript content, while `generated.rs` remains unchanged because the checker did not complete.

This is not a mixed-source state: the reference artifact depends only on TypeScript content, not on story validity.

Strict mode performs no writes. A stale `reference.rs` fails before Cargo story validation, matching the existing generated-file freshness expectation.

## 3. Validate `(map, primaryNpc)`

Keep the current beat header unchanged:

```md
::: story
id: prologue.guild-master
chapter: prologue
map: guild-hall
primaryNpc: guild-master
:::
```

The checker continues validating the map and NPC against generated ID arrays, then adds:

```text
(beat.map_id, beat.primary_npc_id) ∈ NPC_PLACEMENTS
```

A mismatch reports:

- beat ID;
- declared map ID;
- declared primary NPC ID;
- source beat path where available.

Dialogue blocks continue validating their NPC IDs through `NPC_IDS`. No new beat fields are introduced.

## 4. Store beat and map identity once per NPC group

Keep the existing NPC-first runtime shape and extend only `NpcStoryDialogue`:

```rust
pub struct NpcStoryDialogue {
    pub npc_id: String,
    pub beat_id: String,
    pub map_id: String,
    pub branches: Vec<StoryDialogueBranch>,
}
```

Do not copy `beat_id` and `map_id` onto every branch.

The compiler continues grouping by NPC. For the current V1 it must reject compilation if one NPC is encountered across different beat IDs or map IDs, with a diagnostic that says multi-beat or multi-map NPC dialogue requires a separately designed runtime model.

This makes the current one-NPC/one-beat assumption explicit instead of silently flattening incompatible future content.

## 5. Enforce the map invariant in lookup

Keep the current request, response, conditions, priorities, intents, and session IDs.

Lookup becomes:

1. validate locale;
2. find the requested NPC dialogue group;
3. assert `dialogue.map_id == request.map_id`;
4. apply the existing branch-priority logic;
5. return the existing response.

On mismatch, return an explicit error such as:

```text
story npc guild-master is not available on map meadow-entry
```

This is command-boundary hardening, not a newly reachable gameplay feature. `WorldScene` already sends the current map and starts interaction only with a nearby NPC from that map.

The existing test named `treats_map_id_as_context_only_for_now` is replaced with a wrong-map rejection test.

## Tests

### Bun exporter

- renders deterministic sorted Rust source;
- escapes special characters;
- rejects duplicate IDs;
- rejects duplicate placements;
- `--check` passes for exact bytes;
- `--check` fails for stale or missing output;
- failed generation does not partially replace the destination.

### Rust checker/compiler/codegen

- generated reference arrays validate current manifest and beats;
- unknown map, NPC, quest, shop, and enemy behavior remains unchanged;
- `(map, primaryNpc)` mismatch fails with beat context;
- NPC dialogue groups retain one beat ID and map ID;
- conflicting beat or map metadata for one NPC fails compilation;
- generated runtime Rust remains deterministic.

### Runtime command

- correct-map Guild Master lookup succeeds;
- correct-map Mira lookup succeeds;
- wrong-map lookup fails;
- branch priority remains unchanged;
- request/response serialization remains unchanged;
- session IDs remain unchanged.

### Regression gates

- existing story parser, checker, compiler, codegen, and command tests;
- story client and browser-fixture tests;
- quest and shop behavior;
- save compatibility tests;
- `bun run story:check`;
- `bun run story:check:strict`;
- `bun run story:assert-no-frontend-prose`;
- `bun run check`;
- web build;
- Tauri build.

## Compatibility contract

No change to:

- story Markdown headers or prose;
- `StoryDialogueRequest` fields;
- quest-summary booleans;
- branch names or priority;
- intent variants;
- response fields;
- session ID format;
- `MapNpc` shape;
- save schema;
- frontend story-prose secrecy.

The map mismatch path is an internal invariant failure for invalid direct callers. Normal `WorldScene` interactions should behave identically.

## Acceptance criteria

- `reference.rs` is marked generated and reproducible from TypeScript content.
- Draft story checking refreshes it atomically; strict checking rejects stale bytes without writing.
- The generated module contains only current ID sets and NPC placements.
- Existing Rust validation uses the generated arrays without JSON or Serde adapters.
- Every beat's `(map, primaryNpc)` pair resolves to a current map NPC dialogue placement.
- `NpcStoryDialogue` retains one source beat ID and map ID without branch-level duplication.
- Conflicting multi-beat or multi-map reuse of one NPC fails explicitly rather than flattening silently.
- Tauri lookup checks exact map context while preserving all current public interfaces.
- Current story, dialogue, quest, shop, browser fixture, save, web-build, Tauri-build, and frontend-prose behavior remains compatible.
- No unproven story-integration consumer contract ships in HPA-514.

## Definition of done

HPA-514 is complete when copied Rust story IDs are replaced by one generated Rust module, invalid `(map, primaryNpc)` declarations fail at story check, and the Tauri command verifies the existing map-local NPC invariant—without creating a story-to-world platform before a real consumer exists.
